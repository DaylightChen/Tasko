# Tasko — REST API

The HTTP surface exposed by `apps/server`. All routes are mounted under `/api/`. The SSE event stream is at `/api/events`.

The server binds to `127.0.0.1:7373` by default. There is **no authentication** in v1 — the port is local-only and not exposed to the LAN.

All requests and responses are JSON unless otherwise noted. Every error response carries the envelope `{ error: { code, message, details? } }`.

Schemas referenced here are defined in `data-model.md` and live in code under `packages/types/`.

---

## 1. Conventions

### 1.1 Status codes

| Code | Meaning |
|---|---|
| 200 | OK, response body included. |
| 201 | Created, body is the new entity. |
| 204 | No content (rare — used for DELETE / bulk operations with no return body). |
| 400 | Bad request — zod validation failed. `details` carries the zod issue list. |
| 404 | Not found. |
| 409 | Conflict — typically a depth-cap violation or a constraint (e.g., trying to rename Inbox). |
| 422 | Unprocessable — well-formed but semantically invalid (e.g., recurrence rule on a Subtask). |
| 500 | Server error — fs failure, indexer corruption. `details` is logged server-side; user-facing message is generic. |

### 1.2 Error envelope

```json
{
  "error": {
    "code": "ITEM_NOT_FOUND" | "VALIDATION" | "DEPTH_CAP" | "INBOX_IMMUTABLE" | "FS_WRITE" | "DUPLICATE_TAG" | "RECURRENCE_INVALID" | "PARENT_NOT_FOUND" | "INTERNAL",
    "message": "Human-readable; safe to surface in a snackbar.",
    "details": <variable>
  }
}
```

Frontend's API client (`api/client.ts`) parses this envelope. For known codes, the snackbar copy maps to a specific user message; for unknown codes, the generic "Couldn't save. Try again." (per microcopy §28.2) is used.

### 1.3 IDs in paths

All IDs are ULIDs (regex-validated server-side). A malformed ID returns 400 `VALIDATION`.

### 1.4 Timestamps

All timestamps in request/response bodies are ISO 8601 with UTC (`Z` suffix). Dates (`due_date`, `start_date`) are `YYYY-MM-DD` local-date strings, **not** timestamps. Times (`due_time`) are `HH:MM`.

### 1.5 Idempotency

POST endpoints (create) are not idempotent — repeated calls create multiple entities. PATCH endpoints are idempotent (the same patch applied twice has the same end state). DELETE / trash / restore are idempotent.

### 1.6 CORS

```
Access-Control-Allow-Origin: http://127.0.0.1:5173     (dev only; checked against allowlist)
Access-Control-Allow-Origin: http://127.0.0.1:7373     (prod; the same origin)
```

We allow only these two origins. No wildcard.

### 1.7 Authentication

None in v1. Locked decision.

## 2. Items

The workhorse resource.

### 2.1 `GET /api/items` — list items

Query params:

| Param | Type | Notes |
|---|---|---|
| `view` | `'today' \| 'tomorrow' \| 'next7' \| 'inbox' \| 'all' \| 'completed' \| 'project' \| 'tag'` | Optional. If absent, returns all active items (use `view=all`). |
| `project_id` | ULID | Filters to a single project. Required if `view=project`. |
| `tag_id` | ULID | Filters to items tagged. Required if `view=tag`. |
| `parent_id` | ULID \| `'root'` \| absent | If `parent_id=<ulid>`, return children of that item; if `parent_id=root`, return top-level items in the project (combined with `project_id`); if absent, no parent filter. |
| `status` | `'todo' \| 'in_progress' \| 'done'` (repeatable) | Filter by status. Default: all active statuses (todo + in_progress). `view=completed` overrides to `done`. |
| `priority` | `'none' \| 'low' \| 'medium' \| 'high'` (repeatable) | Filter by priority. |
| `sort` | `'due_asc' \| 'priority_desc' \| 'title_asc' \| 'created_desc' \| 'completed_desc'` | Default `due_asc`. `view=completed` defaults to `completed_desc`. |
| `include_completed` | `boolean` | For `view=project`, include completed items in response (used by the "Show N completed" toggle). Default `false`. |

Response 200:

```json
{
  "items": [<Item>, ...],
  "count": <number>
}
```

The server's in-memory index resolves the view server-side:

- `view=today`: items where `(due_date == today AND trashed_at == null) OR (start_date <= today AND today <= due_date AND trashed_at == null)`. Includes overdue (`due_date < today`).
- `view=tomorrow`: items where `due_date == today + 1 AND trashed_at == null`. Excludes multi-day spans whose `start_date > tomorrow`.
- `view=next7`: items where `due_date in [today, today + 7) AND trashed_at == null`, or multi-day spans whose span overlaps that range.
- `view=inbox`: items where `project_id == INBOX AND parent_id == null AND trashed_at == null`.
- `view=all`: items where `trashed_at == null`.
- `view=completed`: items where `status == 'done' AND trashed_at == null`.
- `view=project`: with `project_id` and optionally `parent_id`. Includes all items in the project (server filters by status if `include_completed` is false).
- `view=tag`: with `tag_id`. Includes items whose `tags[]` contains the id.

For "today" inclusion, the server uses **its own local clock** for "today" — we don't accept a date-string from the client for date-driven views (the client and server share a machine, so they agree).

Frontend query keys map 1:1 to these views.

### 2.2 `GET /api/items/:id` — get one item

Response 200: `<Item>`.
Response 404: item not found (also returns 404 if the item is in trash; use `GET /api/trash/:id` for that).

### 2.3 `POST /api/items` — create item

Request body: `ItemCreateSchema` (see `data-model.md` §3.2).

```json
{
  "type": "task",
  "project_id": "01HM...",
  "parent_id": "01HM..." | null,
  "title": "Buy laptop charger",
  "notes": "",
  "due_date": "2026-05-18",
  "start_date": null,
  "due_time": null,
  "priority": "none",
  "status": "todo",
  "tags": [],
  "subtasks": [],
  "recurrence": null
}
```

Server validates:
- zod schema.
- `parent_id` exists (404 PARENT_NOT_FOUND) and is in the same project.
- depth-cap check via `canMove`. Reject with 409 DEPTH_CAP if violation.
- For a Subtask: server rejects POST /api/items with type=subtask (subtasks are inlined; use the subtask sub-routes — see §2.10).

Response 201: the created `<Item>`.

The server stamps `id` (new ULID), `created_at`, `updated_at`, `sort_order` (if not provided), `schema_version: 1`.

### 2.4 `PATCH /api/items/:id` — update item

Request body: partial `ItemPatchSchema` (see `data-model.md` §3.2).

A patch may include `subtasks: [...]` to whole-array-replace the subtasks. (Subtasks have their own sub-routes for efficient individual updates — §2.10.)

Special case: if the patch sets `status` to `'done'` on an item with a non-null `recurrence`, the server performs the **recurring-completion atomic op** (see `data-model.md` §6.5). The response shape becomes:

```json
{
  "completed": <updated source item>,
  "next": <new instance item>
}
```

Frontend's `api/items.ts` checks for this shape.

Validation:
- `parent_id` change: depth-cap check via `canMove`.
- `project_id` change: triggers the cascading project move (see `data-model.md` §3.6).
- Setting `status: 'done'`: stamps `completed_at` server-side.
- Clearing `status` to non-`done`: clears `completed_at`.
- Setting `trashed_at` or `trashed_with` via this endpoint: **rejected (400 VALIDATION)**. Use the trash endpoints (§3).

Response 200: the updated `<Item>`, or `{ completed, next }` for the recurring case.

### 2.5 `DELETE /api/items/:id` — soft-delete (move to trash)

Soft-deletes the item and all its non-trashed descendants atomically. See `data-model.md` §3.4.

Response 200:

```json
{
  "trashed": [<Item>, ...]   // every item moved to trash, with trashed_at and trashed_with set
}
```

If the item doesn't exist or is already in trash: 404 ITEM_NOT_FOUND.

### 2.6 `POST /api/items/:id/restore` — restore from trash

See `data-model.md` §3.4.

Response 200:

```json
{
  "restored": [<Item>, ...]   // the item plus any descendants restored alongside it
}
```

If the item is not in trash: 404.

### 2.7 `DELETE /api/items/:id?permanent=true` — permanent delete (must be in trash)

Hard-deletes from `trash/`. Returns 204.

If the item is not in trash (still active): 400 VALIDATION with message "Item must be in Trash before permanent deletion."

If the item has descendants in trash too (e.g., a cascade-trashed Epic): all `trashed_with=<this id>` descendants are also permanently deleted in the same op.

### 2.8 `POST /api/items/:id/duplicate` — (post-v1, returns 501)

The Duplicate context-menu item is disabled per UX (`interaction-patterns.md` §14, microcopy). The endpoint is **not implemented in v1**. The UI shows the item as disabled.

### 2.9 `POST /api/items/:id/move` — convenience re-parent

Equivalent to PATCH with `parent_id` and/or `project_id`. Exists as a separate endpoint because:

1. The body shape is small.
2. It clearly signals "this is a move" for telemetry / audit / future undo journaling.

Request:

```json
{
  "new_parent_id": "01HM..." | null,
  "new_project_id": "01HM..." | null
}
```

Either may be present; if `new_project_id` differs from the current project, the cascade applies. Depth-cap is checked. Response 200: the updated item.

### 2.10 Subtask sub-routes

Subtasks are inlined on the Item but exposed as their own routes for efficient per-subtask mutations from the modal's subtask list. All sub-routes return the parent Item (with the updated subtasks array) for cache convenience.

#### `POST /api/items/:id/subtasks` — add a subtask

Body: `SubtaskCreateSchema`.
Response 201: the **parent Item** with the new subtask appended.

#### `PATCH /api/items/:id/subtasks/:sid` — patch a subtask

Body: partial `SubtaskSchema`.
Response 200: the parent Item.

#### `DELETE /api/items/:id/subtasks/:sid` — delete a subtask

Permanent (subtasks don't go to trash independently). The parent Item's `subtasks` array shrinks.
Response 200: the parent Item.

## 3. Trash

### 3.1 `GET /api/trash` — list trashed items

Query params:

| Param | Type | Notes |
|---|---|---|
| `sort` | `'trashed_desc' \| 'title_asc'` | Default `trashed_desc`. |

Response 200:

```json
{
  "items": [<Item>, ...],
  "count": <number>
}
```

Only top-level trashed items are returned by default — descendants whose `trashed_with` points to a trashed parent are hidden in the list view (they appear nested if the user expands; v1 ships flat — the descendants are implicit, restored with the parent).

To list ALL trashed items (including cascaded descendants), pass `?flat=true`.

### 3.2 `GET /api/trash/:id` — get one trashed item

Response 200: `<Item>` (with `trashed_at` set).

### 3.3 `POST /api/trash/empty` — empty trash

Permanently deletes every item in `trash/`. Returns 200:

```json
{ "deleted_count": <number> }
```

This is the "Empty Trash" action. Confirmation is the UI's responsibility.

## 4. Projects

### 4.1 `GET /api/projects` — list projects

No query params (the user has a manageable count; we return all). Includes Inbox at the top.

Response 200:

```json
{
  "projects": [<Project>, ...],
  "count": <number>
}
```

Sort order: Inbox first, then user projects by `sort_order` ascending. Within a folder, projects are by `sort_order`.

### 4.2 `GET /api/projects/:id` — get a project

### 4.3 `POST /api/projects` — create a project

Body: `ProjectCreateSchema`.

```json
{
  "name": "Q3 Launch",
  "folder_id": null,
  "is_hierarchical": true,
  "color": null,
  "icon": null
}
```

Response 201: `<Project>`.

Validation:
- Unique name? **No constraint** — duplicates allowed (users may have multiple projects with similar names; we don't impose).
- `folder_id` must exist if non-null.

### 4.4 `PATCH /api/projects/:id` — update a project

Body: partial `ProjectPatchSchema`. The user may toggle `is_hierarchical` after creation (per UX flow §12 / spec §7.14 — the project lifecycle supports this).

Validation:
- If `id == INBOX`, reject any field change with 409 INBOX_IMMUTABLE.

Response 200: the updated `<Project>`.

### 4.5 `DELETE /api/projects/:id` — delete a project

Server cascade:

1. Enumerate all items in the project (active + completed).
2. Soft-delete each (move to trash, set `trashed_at` and `trashed_with: <project id>` — note: project id is the cascade anchor, even though it's not an ItemId; we accept this overlap because `trashed_with` is just a coordination key).
3. Delete the project file.

Atomically (single mutex).

Response 200:

```json
{
  "deleted_project_id": "<id>",
  "trashed_items": <count>
}
```

Inbox: 409 INBOX_IMMUTABLE.

Restoring a trashed project is **not in v1** — projects, once deleted, are gone. Their items are recoverable from trash but get reparented to Inbox on individual restore. (We document this in `open-questions.md` as a v1.1 question — should project restore be added?)

## 6. Tags

### 6.1 `GET /api/tags` — list

Query params:

| Param | Type | Notes |
|---|---|---|
| `prefix` | `string` | Optional. Autocomplete: returns tags where `name_lower.startsWith(prefix.toLowerCase())`. Capped at 50 results. |
| `include_orphans` | `boolean` | Default `false`. If false, only tags referenced by at least one active item are returned (the sidebar list). |

Response 200:

```json
{
  "tags": [<Tag>, ...],
  "count": <number>
}
```

### 6.2 `POST /api/tags` — create (or get existing)

Body:

```json
{
  "name": "urgent"  // or "#urgent" — leading # stripped by server
}
```

Server:
1. Lowercase + strip `#` to compute `name_lower`.
2. If a tag with this `name_lower` exists, return it (200 with existing, **not** 201) — this is the "find-or-create" pattern.
3. Else create with the user-typed name (preserving casing in `name`), `name_lower` as computed.

Response 200 (existing) or 201 (new): `<Tag>`.

### 6.3 `GET /api/tags/:id` — get a tag

### 6.4 `DELETE /api/tags/:id` — delete a tag (post-v1, returns 501)

Not implemented in v1 (no tag management UI). The endpoint shape is reserved.

### 6.5 `GET /api/tags/autocomplete?q=...` — convenience alias for `GET /api/tags?prefix=...`

Returns the same shape. Frontend uses this for the modal's tag input.

## 7. Bulk operations

### 7.1 `POST /api/bulk/move-overdue-to-today` — move all overdue to today

No body (or `{ scope: 'all' }`). Server enumerates active items where `due_date < today`, sets `due_date = today` for each. Atomic (single mutex).

Response 200:

```json
{
  "moved_ids": [<ItemId>, ...],
  "moved_count": <number>,
  "new_due_date": "2026-05-18"
}
```

If `moved_count` is 0, response is still 200 with empty array.

### 7.2 `POST /api/bulk/move-to-project` — bulk re-parent across project (multi-select)

Body:

```json
{
  "item_ids": ["<ulid>", ...],
  "new_project_id": "<ulid>",
  "new_parent_id": "<ulid>" | null
}
```

Each item (with its descendants) cascades into the new project. Depth-cap validated per-item.

If any single item fails the depth-cap, the whole operation is rejected (transactional). Response: 409 with details of which item failed.

Response 200:

```json
{
  "moved_count": <number>,
  "items": [<Item>, ...]
}
```

### 7.3 `POST /api/bulk/delete` — bulk soft-delete

Body:

```json
{ "item_ids": ["<ulid>", ...] }
```

Each item (with its descendants) cascades into trash.

Response 200:

```json
{
  "trashed_count": <number>,
  "items": [<Item>, ...]
}
```

### 7.4 `POST /api/bulk/complete` — bulk mark complete

Body:

```json
{ "item_ids": ["<ulid>", ...] }
```

Sets `status: 'done'` on each. For items with non-null `recurrence`, generates next-instances (each within the same mutex).

Response 200:

```json
{
  "completed_count": <number>,
  "new_instances": [<Item>, ...] | [],
  "items": [<Item>, ...]
}
```

If any of the items has incomplete subtasks, the bulk complete still proceeds (the UI's "parent completion blocking" prompt is per-item; if the user triggered this bulk action they've confirmed). UX may surface aggregate "Completed N tasks and M subtasks."

## 9. Server-sent events

### 9.1 `GET /api/events` — SSE stream

Standard SSE with `Content-Type: text/event-stream`. Heartbeat ping every 25 seconds (comment line `: ping`) to keep proxies/dev servers happy.

Each event:

```
event: item.changed
data: {"id":"01HM...","source":"self|other-tab","timestamp":"..."}
```

The `source` field is determined by a `?tab_id=<random>` query param the client sends on connect; the server tags each event with the tab id of the tab that triggered it. Other tabs see `source: 'other-tab'`.

Event types:

| Type | Payload |
|---|---|
| `item.created` | `{ id, source, timestamp, item: <Item> }` |
| `item.changed` | `{ id, source, timestamp, item: <Item> }` |
| `item.trashed` | `{ id, source, timestamp, item: <Item> }` (item has trashed_at set) |
| `item.restored` | `{ id, source, timestamp, item: <Item> }` |
| `item.permanently_deleted` | `{ id, source, timestamp }` (no item — it's gone) |
| `project.created` | `{ id, source, timestamp, project: <Project> }` |
| `project.changed` | `{ id, source, timestamp, project: <Project> }` |
| `project.deleted` | `{ id, source, timestamp }` |
| `folder.created` | `{ id, source, timestamp, folder: <Folder> }` |
| `folder.changed` | `{ id, source, timestamp, folder: <Folder> }` |
| `folder.deleted` | `{ id, source, timestamp }` |
| `tag.created` | `{ id, source, timestamp, tag: <Tag> }` |
| `tag.changed` | `{ id, source, timestamp, tag: <Tag> }` |
| `config.changed` | `{ source, timestamp, config: <Config> }` |
| `trash.emptied` | `{ source, timestamp, deleted_count }` |
| `bulk.completed` | `{ source, timestamp, count, affected_ids }` |

Frontend's SSE client (`api/events.ts`) dispatches each event to TanStack Query as a `queryClient.invalidateQueries(...)` or `queryClient.setQueryData(...)` per type.

### 9.2 Reconnection

The frontend `EventSource` reconnects automatically. On reconnect, the frontend forces a refetch of every active query (cheap; the server is local). We do not implement an event-id / replay protocol in v1 — the cost of being a few milliseconds stale during reconnect is acceptable.

### 9.3 Whether to ship SSE in v1

Yes, ship. See `architecture.md` §2.7 for the rationale.

If the implementation turns out to add complexity that costs us elsewhere, drop SSE and rely on `refetchOnWindowFocus: true` from TanStack Query. The fallback already covers the "tab regains focus" case.

Response 200:

```json
{
  "ok": true,
  "version": "1.0.0",
  "data_dir": "/Users/zen/tasko-data",
```

In production, the server serves the Vite build output (`apps/web/dist`) at `/`. In dev, the user hits `http://127.0.0.1:5173` (Vite's dev server) which proxies `/api` to the server.

## 11. Validation specifics

### 11.1 Title length / character set

`title`: 1-500 chars, UTF-8 safe. We allow any printable character including emoji (per microcopy "no emoji in OUR copy" — user content is the user's choice).

### 11.2 Date validity

`due_date`, `start_date`: `YYYY-MM-DD` regex; server additionally checks that the date is a valid calendar date (Feb 30 → 400). The check uses `new Date(y, m-1, d).getMonth() === m - 1` to detect rollover.

### 11.3 Time validity

`due_time`: `HH:MM` regex. We don't store seconds.

### 11.4 Tag length

`name`: 1-32 chars. Match `name_lower` against existing tags case-insensitively.

### 11.5 Notes length

`notes`: max 50,000 chars. Server rejects beyond.

### 11.6 Subtask count

No hard cap in v1. (The UI gets unwieldy past ~50; we don't reject server-side.)

### 11.7 Recurrence rule consistency

`weekly` requires `weekdays.length >= 1`.
`monthly` requires `day_of_month in [1, 31]`.
`yearly` requires `month in [1, 12]` and `day in [1, 31]`. The server doesn't reject Feb 30 in yearly — it clamps at compute-time (see `data-model.md` §6.3).
